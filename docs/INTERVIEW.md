# Interview notes: gtm-brain

Every number below comes from a file in this repo. Paths are in brackets. Data is public homepage text of 25 DTC brands, plus 19 held-out domains, plus synthetic eval cases. The ICP and the offer are synthetic.

## 1. What is it, in one minute?
gtm-brain takes a CSV of company domains and returns one checked opening line per good-fit company. It fetches two public pages per domain, profiles the company, scores it against a YAML ICP, writes a line with a verbatim evidence quote, and checks the line. A human approves rows in approvals.csv. Only approved rows export to Instantly and HubSpot CSVs. It ships as a Claude Code plugin (skills, slash commands, MCP server, hook) and as a CLI that runs the same code. [README.md, plugin/]

## 2. Why a Claude Code plugin with MCP, and not a script or a Clay table?
The same functions serve three callers: the MCP server for interactive work in Claude Code, the CLI for cron or n8n, and the offline tests. The skills tell Claude which tool order to use and which rules never bend. The hook enforces approval outside the model, so a bad prompt cannot skip it. Clay is faster to start with for enrichment waterfalls. I built this to own the logic, the checks and the cost per row. [gtm_brain/server.py, plugin/skills/, plugin/hooks/]

## 3. How do you stop the model from inventing facts?
Four layers, and none is a guarantee. The writer must return a quote copied from the fetched text, and code checks the quote is a verbatim substring (case and whitespace normalised). A banned-phrase filter rejects clichés, dashes and lines over 30 words. A Haiku claim checker compares the line to the quote and must find every fact in it. If the checker returns something unparseable, the line fails. One rewrite is allowed with the checker's complaints, then the account is dropped. Limit: code proves only that the quote is verbatim. The Haiku checker judges the rest and misses small additions. In the live run the glossier.com line said "best foundation for makeup" while its quote ended at "best foundation", and it passed. Harry's ("its founders"), Ritual ("for its supplements") and held-out girlfriend.com ("activewear fabrics") slip the same way. [runs/2026-10-24-live/first_lines.csv, runs/2026-10-24-heldout/first_lines.csv] [gtm_brain/lines.py, tests/test_lines.py]

## 4. How was the LLM judge (claim checker) calibrated?
**Takeaway: the shipped checker caught 5 of 6 padded lines, in-sample (tuned on the same 30 lines, one labeler). The 24 of 24 on easy synthetic cases proves little.**

I wrote 24 labeled synthetic cases (12 faithful, 12 with one injected unsupported claim). Haiku scored 24 of 24. Weak evidence: the cases are easy and I wrote them. [evals/claim_checker_cases.jsonl, evals/checker_results.json] Then I hand-labeled 30 real passed lines: 24 faithful, 6 padded. The first prompt caught 0 of 6, so 20 percent of its passes were false by my strict read. [evals/real_lines_labeled.jsonl] I tightened the prompt: it catches 5 of 6 and wrongly fails 2 of 24 faithful lines. A stricter draft caught 6 of 6 but failed 10 of 24. The miss is buffy.co. [evals/real_lines_rescored.json, evals/real_lines_rescored_strict.json] Held-out v2 with the shipped prompt: 9 of 11 first try, 10 of 11 kept, all 10 read as faithful. [runs/2026-10-24-heldout-v2/metrics.json] For production: a second labeler and 100 or more fresh lines.

## 5. Why this model routing?
Haiku 5.5 does the high-volume, structured reading: profile, ICP judgment and claim check. Sonnet 5.5 writes the line, because wording is where quality shows. The split in the live run: Sonnet $0.2853 and Haiku $0.1261 of $0.4114. [runs/2026-10-24-live/metrics.json] I did not run Opus. I have no data that it improves lines, and the verbatim and checker gates already bound the error. The model ids are env-configurable (GTM_MODEL_FAST, GTM_MODEL_WRITER). [gtm_brain/llm.py]

## 6. What does it cost?
Live run, 25 accounts: $0.4114 total, $0.0165 per account, $0.0242 per approved line (17 approved). [runs/2026-10-24-live/metrics.json] The line writer is the biggest stage at $0.2853 of 19 calls, since it reads the fetched page text each time (`gtm_brain/lines.py`). [runs/2026-10-24-live/cost_report.json] If the rate held, 1,000 accounts would cost about $16.50 (the held-out run gives $17.46). That is an extrapolation, not a measurement, and fetch failures and the A/B filter would change it. Rates are assumed list prices in pricing.yaml, and the whole project spent $3.49 against a $6 cap. Build against Clay list prices is in docs/build-vs-buy.md. [runs/ledger.jsonl]

## 7. What fails, and why?
Six of 25 domains returned nothing: two 429 rate limits, three 403 bot blocks, one robots.txt disallow. [metrics.json, fetch_errors] I honor those and do not rotate user agents. In the first full run (thinking off for Haiku only) the Sonnet writer returned no parseable line for 7 of 18 accounts, which I believe was because it spent its output budget on thinking. That cause comes from my own reading of the failure and the comment in llm.py; the run artifact shows only the 7 dropped rows with empty lines. I then set thinking per model: `disabled` for Haiku, and `between_tools` for Sonnet, because the API rejected `disabled` for Sonnet 5.5. So thinking is not literally off for both; I did not measure how much `between_tools` thinking costs. [runs/2026-10-24-v1-baseline/, gtm_brain/llm.py] In the second run 0 of 18 lines passed first try, because the writer added claims beyond its quote, which the checker flagged (see first_problems). [runs/2026-10-24-v2-thinking-fix/first_lines.csv] I did not verify whether those claims were true. I fixed the writer prompt. v1 and v2 both cost $0.6827 in total, a coincidence; per-model figures differ. [runs/2026-10-24-v2-thinking-fix/metrics.json]

## 8. Your first-try pass rate is 94 percent. Is that real?
Say it in three lines: 94 percent is in-sample with the first checker prompt. With the shipped prompt, the same 25 domains give 78 percent first try (14 of 18, `runs/2026-10-24-live-v2/`), and held-out v2 gives 9 of 11. Quote the lower numbers.

The 94 percent is in-sample: I tuned the writer prompt on the same 25 domains. So I ran 19 new domains once with no tuning, using the first checker prompt (held-out v1). The checker passed 13 of 13 lines first try. [runs/2026-10-24-heldout/metrics.json] My hand labels found 12 faithful and 1 that adds words beyond its quote (girlfriend.com), so the checker is lenient. [evals/real_lines_labeled.jsonl] Both samples are small: 18 and 13 lines, so one line is 5 to 8 points. The history of 22, then 0, then 94 percent shows the prompt matters a great deal. [docs/index.html] For a real claim I would hold out 50 or more domains, hand label every line, and report a range.

## 9. How does the human approval work, and can it be bypassed?
The pipeline writes approvals.csv with an empty approved column. Export refuses to run with no yes, both inside export_sequence and in a Claude Code PreToolUse hook that matches the MCP tool and Bash commands that call export. The hook is stdlib only and exits 2 to block. [plugin/hooks/require_approval.py, tests/test_approval_export.py] It can be bypassed by editing approvals.csv, so it is a process control and not security. In the demo transcript I approved with a flag as the builder. That was not a real review. [runs/2026-10-24-live/approval_demo.txt]

## 10. How is it scraped responsibly, and what about GDPR?
It reads robots.txt first, uses an honest user agent, fetches at most two pages per domain, waits between requests and caches results. A robots 5xx counts as blocked (code in `_allowed`, test `test_robots_5xx_counts_as_blocked`). A robots.txt that cannot be reached at all counts as absent. It collects company-level text only: no people, no emails. The Instantly export has an empty email column to fill from an enrichment tool. Some homepage text names founders, and I would filter names out before using lines in production. [gtm_brain/fetch.py, tests/test_parsing_fetch.py]

## 12. What would you do next, and what are the limits?

CRM and sending, in detail: `gtm-brain hubspot` upserts companies by domain with a dry-run default (dry-run payloads in the run folder). `gtm-brain check-domain` reads SPF, DMARC and DKIM. Payloads follow HubSpot's public CRM v3 companies API (search on domain, then create or patch, so re-runs update instead of duplicating). There is no Salesforce path and no Instantly API push, only CSV with UTM tags. For production I would add a real HubSpot sandbox test, retries with backoff, a queue instead of a thread pool, warmup and bounce tracking, and a reviewer UI. Buy the data layer (email finding, waterfalls, intent) from Clay or a vendor; numbers in docs/build-vs-buy.md. [gtm_brain/hubspot.py, gtm_brain/deliverability.py, n8n/gtm-brain-weekly.json]
The lines restate a homepage sentence. They are an opening, not deep personalization, and they do not use trigger events or hiring data. Platform detection reads HTML signals (`gtm_brain/enrich.py` also reads email/SMS, reviews, helpdesk, analytics tools and a careers link from the fetched HTML, tested on saved fixtures; only held-out v2 has it), so headless or heavily scripted shops can be missed. Lifecycle exists in small form: `gtm-brain lifecycle` tags accounts new, waiting, stale (over 30 days) or replied from a CSV, and drafts a follow-up for stale accounts only if the account was human approved and has a verified line. It is rule-based with no LLM call and no reply tracking, shown on 6 synthetic dates in runs/2026-10-24-lifecycle/. [gtm_brain/lifecycle.py, tests/test_lifecycle.py] The ICP is synthetic and the weights are my guess, not fitted to replies. Next: log reply rates by tier to fit the weights, add a second evidence source per account, and test line variants against replies. Cost and time per account are measured here; reply rate is not, and I make no claim about it.
